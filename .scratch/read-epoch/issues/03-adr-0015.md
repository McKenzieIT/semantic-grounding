## Question

**ADR-0015 + GLOSSARY「读 epoch」词条。**

把 charting 的新鲜度边界裁决落进 ADR + GLOSSARY，作为实现票（04）的强制前置。

**ADR-0015 裁决面（草稿，grilling 定稿）**：

- R1 键复合：`(per-call epoch) × 进程内 corpusVersion`，两半各有可证的必要性
- R2 epoch 由 `AsyncLocalStorage` 环境式提供，substrate 内一处进入
- R3 未开 epoch 时 `loadTables` / `loadEvents` 行为与今天逐字节相同（缓存纯增量开关）
- R4 写位形状 `{ ...raw, field: value }`（spreading）是复合键成立的必要前提——写位若就地改 `raw`，epoch 共享对象会丢写
- R5 别名风险实测为零（7 处写位全部 spread，无就地改）
- R6 否决 mtime 校验式跨调用缓存（拿正确性换性能）
- R7 否决 `corpusVersion` 单独做键（看不见跨进程写，`concurrent-write.spec.ts` 实测）
- R8 否决纯 per-call epoch（写位之间隔写，会静默丢写）
- R9 读 epoch 是 MCP 只读路径的缓存；`snapshot.ts` / `withSnapshot` 是 dsh MVCC 的缓存，两套生命周期需求不同，不合并
- R10 本裁决不触碰 ADR-0004 裁决 8（写门指纹走 `definitionVersion` → `readFileSync`，不经 loader）

**关系**：

- ADR-0004 裁决 8（写门指纹）：**不受影响**，明确排除
- ADR-0005 裁决 6（拒绝快照句柄进 MCP 读面）：**与本裁决互补**——snapshot 服务 dsh，epoch 服务 MCP
- ADR-0006 裁决 4（work_id 自包含指纹）：指纹**吃 loader 输出**，故本裁决对 memo 形态是硬约束

**GLOSSARY 新词条**：

- `读 epoch` / `read epoch`：一次工具调用内，loader 输出的缓存作用域；与进程内 `corpusVersion` 组成复合键，关掉跨进程过期窗口；调用结束即销毁
