# #33 护栏候选规则的全库实测 —— 一次性探针

> **PROTOTYPE / 一次性代码，不进 `main`。** 本目录是为回答 [#33](https://github.com/McKenzieIT/semantic-grounding/issues/33)
> 造的测量探针，答案已回到票上，代码留作一手凭据。`packages/` 下未改动任何文件。

## 这个探针回答什么

[#26](https://github.com/McKenzieIT/semantic-grounding/issues/26) 提了一组「候选拒收规则」来止住抽取器把描述片段
撕成别名。问题是：**这组规则在真语料上到底杀掉什么、会不会误杀真业务词、以及护栏之后还剩多少量要靠
[#36](https://github.com/McKenzieIT/semantic-grounding/issues/36) 的否决权兜。** 这三个数只能测，不能推。

## 怎么跑

```bash
cd /tmp/sg-guardrail-probe                      # 或本目录
TSX=/path/to/semantic-grounding/packages/substrate/node_modules/.bin/tsx

$TSX probe.ts        # 生成 out/probe-data.json（基线 + 逐规则归因）
$TSX validate.ts     # 回放 3cef160，证明基线不是复刻猜测
$TSX final.ts        # 打印 writeup 里的全部数字
$TSX build-html.ts   # 生成 out/report.html —— 给人看的那张差集表
open out/report.html
```

`report.html` 是自包含单文件：**每条规则一个开关、长度上限一根滑杆**，勾选即重算杀/活两栏和独杀数。
规则集 → 杀掉集这个状态机，就是 #35 要裁的东西，所以做成可拨的而不是一张死表。

## 两个前提更正（先说，因为后面的数都建在上面）

1. **语料不是「321 表 + 453 events」，是 321 表 + 446 events。** `events/` 下是二级目录，
   453 个 YAML 里有 7 个 `_index.yaml`，loader 跳过它们。本票票面写的 453 需要更正。
   （探针实际解析到 445 个事件定义 + 321 表 = 766 个定义；第 446 个事件在加载期被过滤，不影响结论。）
2. **污染不是「全库弥漫」，而是几乎全在 events 里。** `git show --name-only 3cef160` 是
   **445 events + 1 table**：那 1 张表才是当时 `run_enrichment` 的本意，445 个事件是
   [#25](https://github.com/McKenzieIT/semantic-grounding/issues/25) 维度过滤缺陷的连带写入（已在 map #27 修掉）。
   所以「446 个被污染定义」说的是**写入面**，不是**污染源**。

## 探针保真度（为什么可以信下面的数）

两道独立校验，都是硬复现，不是抽样：

| 校验 | 做法 | 结果 |

| 基线 == 线上实际写入 | 对 `3cef160` 触及的每个事件文件，取 `3cef160^` 的状态，跑**真的** `discoverAltLabelsDeterministic` + **真的** `mergeAltLabels`，与磁盘 HEAD 比对 | **445 / 445 全等** |

第二道是关键：它证明基线复现的是**线上那次污染写入本身**，而不是我对抽取器的理解。

> 中途这道校验先读出 439/445、6 个不明失配。没有接受这个模糊数，而是去看了

## 结论二：疑似假阴性 —— 105 个词，没有一个是真业务别名

这是本票最该被人眼验的一栏。判据是「被杀 + 形状像真业务词」，然后扣掉**纯同一性命中**
（这个词就是本定义自己的某个列名 —— 那是同一性判断，不是业务判断，817 次 / 347 个词，
**该类含中文的词 0 个**，中文业务词零风险）。

剩下 **166 次 / 105 个词**，全表在上面。通读之后的判定：**没有一条是真业务别名。** 它们全部是：

- **字段枚举**：`等级/vip/战力/经验`、`天数/次数/时长`、`武将/装备/战法/法宝`
- **存储与分区说明**：`日全量快照 _df`、`按 ds 更新日期分区`、`_arch 归档快照版`、`无 ds 分区，静态全量`
- **分层标记**：`dim`、`dws`、`di`、`df`
- **字段释义**：`卡池ID，业务唯一标识`、`订单号，主键，全局唯一`、`道具名称，人类可读`
- **粒度元组**：`每行=一个评估样本角色`、`设备ID+区服+日期`、`角色+统计日`
- **口径算式**：`累计付费 / 设备数`、`成功率~93.4%`、`用于参与率/胜率计算`

唯一两个可争议的是 `p0601` / `p0602`（游戏内容编号，被 `digit-run` 杀）。若判它们是真标识符，
`digit-run` 需要放宽；它全库独杀只有 6 条，放宽的代价很小。

### 票面点名必须存活的词，实测

| 词 | 结果 |
|---|---|
| `DAU` | 作为候选出现 **3 次，3 次全存活** ✓ |
| `现金券` | 作为候选出现 **1 次，存活** ✓ |
| `GMV` / `T+1` / `ARPU` / `LTV` / `留存率` / `客单价` | **从来不是候选** —— 它们在描述里是白文，不在括号/引号/`domains` 内，抽取器根本不碰，护栏无关 |

`T+1` 尤其值得记：票里担心 `+` 规则会伤到它，实测它**全库作为候选出现 0 次**，这个顾虑不成立。

## 结论三：五条新增规则，实测零中文业务词风险

存活侧最大的垃圾类是**斜杠连接的字段枚举** —— `/` 不在 #26 的分隔符集里。按独杀排序：

| 新规则 | 独杀 | 命中里含中文的词种 | 为什么安全 |
|---|---:|---:|---|
| A `/` 也算分隔符 | +241 | 250 | 含中文但全是枚举串（`等级/vip/战力`），不是单个业务词 |
| B 分层/存储后缀 | +169 | **0** | 白名单只有 7 个词：`df`/`di`/`mi`/`od`/`arch`/`dim`/`dws` 系 |
| C 列名 snake/camel 归一 | +66 | **0** | 描述写 `role_id`，`params_fields` 里的键是 `roleId` —— 同一个词，原规则漏判 |
| D `+` 复合键记法 | +13 | 7 | `ds+tag_type`、`设备ID+区服+日期`；`T+1` 全库 0 次 |
| E 箭头 / 波浪号 | +4 | 5 | `成功率~93.4%` 一类算式 |

合计 4296 → **杀 2193（51.0%）/ 活 2103（49.0%）**，较原始 9 条 **+493**。

### 两条规则形状上的发现，直接影响 #35 怎么裁

1. **`own-column-name` 应当被 `column-name-canon` 取代，而不是并存。** 归一版是严格超集
   （859 ⊇ 793），一旦开启，原规则独杀归 **0**。
2. **长度上限几乎不重要。** 结构性规则齐备后，cap 从 12 调到 50，总杀掉只在
   **51.7% ↔ 50.9%** 之间动，不到一个百分点；cap=24 的独杀是 **5 条**。
   #35 不必在这个数字上花时间。
3. **`partition-kv` 完全冗余**（独杀 0），`pure-digits` 全库只命中 6 条、独杀 1 条。
   两条都是 #26 的招牌候选，在真语料上近乎空转。

### 一条听起来有理、实测否决的规则

**F「不要把自身 id 的子串重新抽成别名」** —— 原则上很顺，独杀 92 条，看着很有产出。
实测它杀掉 `tactic`、`charm`、`toy`、`rank`、`conquest`、`homeland`、`mission`：
**英文系统名，恰恰是最有价值的别名类**，而它们之所以是 id 的子串，正因为定义 id 就是由它们拼出来的。
标 `tier: 'rejected'`，不计入建议集。留在 `rules.ts` 和 viewer 里可拨，便于 #35 复核这个否决。

## 结论四：#36 的否决集规模（本票的阻塞边交付）

护栏生效后仍会被重抽的剩余量：

| 来源 | 存活次数 | 存活词种 |
|---|---:|---:|
| `domain` | 922 | **10** |
| `paren` | 1139 | 667 |
| `quote` | 42 | 36 |
| **合计** | **2103** | **711** |

**否决集规模：按 (定义, label) 键 ≈ 2103 条；按 label 全局键 ≈ 711 条。**

`domain` 分支全库只有 10 个词（`自定义`×162、`角色成长`×144、`战斗关卡`×128、`系统监控`×95、
`付费经济`×93、`用户生命周期`×90、`装备道具`×72、`探索收集`×66、`社交公会`×54、`资源产销`×18），
且它们**永远会被重抽** —— 只要 `domains` 字段还在，每轮 enrichment 都会重新提出这 10 个词。

这就是 map #32 已核事实 8「护栏尺寸决定否决权尺寸」的实测取值：**窄机制那一支是可达的。**
否决权只需要能压住 `domains` 词 + `deterministic` 关系引用，不需要承载任意垃圾。
与 [#34](https://github.com/McKenzieIT/semantic-grounding/issues/34) 的研究结论对上了 ——
各家数据目录都不压缩否决集，因为其规模被资产数界住；711 这个量级同样不需要压缩或过期机制。

## 顺带发现（不在本票范围内解决，只记录）

1. **抽取器有一个召回缺陷。** `关卡名，如"汉家军阵"` 里，`汉家军阵` 是个**真正好**的别名，
   但它嵌在括号夹注内部，抽取器只拿到整条 `关卡名，如"汉家军阵"` 然后被护栏杀掉，
   干净的那个词从未被单独抽出。护栏不制造这个问题，但也不解决它。
2. **文档与实现不符。** `discoverAltLabelsDeterministic` 的 docstring 称确定性轮会用列注释，
   实际只用 `description`（或 `table_comment`）+ `domains`；列注释只出现在 LLM 轮的 prompt 里。
3. **引号正则的开合字符类不对称。** 开类 `["'「《]`、闭类 `["'」》]` —— `"` 能开、`」` 能闭，
   会产出跨配对的区间。`quote` 分支全库只有 59 条，影响面小，但是个真缺陷。
4. **`domains` 没有长度上限**，只有 `>= 2`；候选长度上限只作用在括号/引号两支上。
